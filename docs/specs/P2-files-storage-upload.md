## 1. Overview & Architecture Boundary

Per `AGENTS.md` and the architecture decision of 2026-10-25 (DB1 named Firestore database `atrium-1`), Firebase Cloud Storage rules cannot query named Firestore databases via `firestore.get()` or `firestore.exists()` (Storage rules only support the `(default)` database).

Consequently, direct client reads and writes to Cloud Storage are completely denied by `storage.rules`. All file uploads and downloads are strictly mediated by authenticated Cloud Functions callables using short-lived V4 signed URLs and the Admin SDK:

1. **Strict Deny Rules (`storage.rules`)**:
   - Denies all direct client reads and writes across all paths (`allow read, write: if false`).
   - Prevents unauthenticated access, unmetered uploads, token leakage, or unauthorized downloads.
2. **Canonical Storage Hierarchy**:
   - `boards/{boardId}/items/{itemId}/files/{fileId}`.
3. **Upload Flow (Two-Step Callable with V4 Signed URLs)**:
   - **Step 1 (`requestFileUpload`)**:
     - Client calls callable with `{ boardId, itemId, columnId, fileName, contentType, size }`.
     - Validates board edit permission using the shared `resolveBoardRole` helper.
     - Validates `size <= 100 MB` and `size <= settings.maxFileSizeMb * 1024 * 1024`.
     - Validates `isFileAllowed({ name: fileName, size, mimeType: contentType }, settings)`.
     - Checks active item state and max 100 files limit.
     - Generates unique safe `fileId` (`^[A-Za-z0-9_-]{1,128}$`).
     - Signs upload URL with V4 `action: 'write'`, 10 min expiry, and `extensionHeaders: { 'x-goog-content-length-range': '0,' + size }`.
     - Returns upload URL, expiresAt, and required headers so GCS rejects any upload exceeding `size` at the HTTP boundary.
   - **Step 2 (`finalizeFileUpload`)**:
     - Client PUTs file directly to GCS via the signed URL.
     - Client invokes `finalizeFileUpload` with `{ boardId, itemId, columnId, fileId, fileName }`.
     - Callable verifies object metadata in GCS (`size`, `contentType`, `timeCreated`).
     - If validation fails or 100-file cap is reached, the transaction returns `{ kind: 'rejected', storagePathToDelete }`.
     - Storage delete runs strictly **after** `runTransaction` resolves, guaranteeing no deletions occur inside transaction retry loops.
     - On success, atomically commits `FileAttachment` to Firestore `values.<columnId>` using Admin SDK transaction.
4. **Download Flow (`getFileDownloadUrl`)**:
   - Client invokes `getFileDownloadUrl` with `{ boardId, itemId, columnId, fileId }`.
   - Validates read access (`owner`, `editor`, `viewer`) using `resolveBoardRole`.
   - Confirms item is not deleted (`state !== 'deleted'`) and `fileId` is present in the item cell.
   - Generates a short-lived V4 signed GET URL (`action: 'read'`, 5 min expiry).
   - No permanent `getDownloadURL` public tokens are created.
5. **Delete Flow (`deleteFileAttachment`)**:
   - Validates edit permission on the board.
   - Ensures `fileId` is present in the specified column cell.
   - Commits removal from Firestore item cell inside the transaction.
   - Returns `storagePathToDelete` from transaction; deletes object from Cloud Storage strictly **after** the transaction commits (`ignoreNotFound: true`).
6. **Orphan Sweeper Strategy (`purgeOrphanUploads`)**:
   - An upload initiated via `requestFileUpload` where the client never calls `finalizeFileUpload` (e.g. browser crash, aborted upload) produces an unreferenced storage object.
   - **Strategy**: A daily scheduled Cloud Function `purgeOrphanUploads` runs at 03:00 UTC. It scans all objects under `boards/` older than a 1-hour cutoff. For each candidate, it verifies whether the object path is referenced in the item's `files` cell. If no reference exists (or item was removed), the orphan object is purged from Cloud Storage.
7. **Server-Managed Column (FW2)**:
   - `files` column is marked `serverManaged: true`.
   - Direct client writes to `values.<filesColId>` are rejected by `firestore.rules` and `validateCell`.

## 2. Security Rules (`storage.rules`)

```
rules_version = '2';

// Atrium Cloud Storage security rules.
// Architecture & DB1: Atrium uses the named Firestore database atrium-1 (eur3).
// Storage rules' firestore.get() can only read the (default) database, so direct
// client access to storage paths is completely denied. All uploads and downloads
// go through short-lived V4 signed URLs generated by Cloud Functions callables
// with full workspace and board RBAC authorization.
service firebase.storage {
  match /b/{bucket}/o {
    match /{allPaths=**} {
      allow read, write: if false;
    }
  }
}
```
