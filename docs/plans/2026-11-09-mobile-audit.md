# Mobile audit (M0): what the phone harness found

Date: 2026-11-09. Roadmap: "Mobile pass", step M0 (see `docs/plans/2026-11-09-next-steps.md`). This PR adds tooling and this audit; it does not change the app. M1 fixes the defects below and shrinks `tests/visual/src/mobile-known-defects.json` as it goes.

## How it was measured

- `tests/visual/src/mobile-audit.spec.ts` (Playwright project `mobile-audit`, WebKit, `devices['iPhone 15']`) opens 20 screens at 375×667, 390×844, 430×932, 360×800 and 768×1024: 100 tests (at 768 the sidebar is permanent, so its "drawer" test just measures the sidebar).
- Checks: `overflow-x` (page scrolls sideways), `offscreen-x` (an element straddles a screen edge with no scroll container around it), `topbar-covered` (something painted over the top bar on a plain page), `topbar-moved` and `scroll-leak` (the top bar moved, or the page or visual viewport scrolled, after scrolling inside an open dialog or panel), `input-font-size` (a text field under 16 px, which makes iOS Safari zoom in).
- The findings below were recorded on macOS WebKit (Playwright's WebKit build). The CI list must be confirmed on Linux; see "Caveats".

## The notification-settings bug

The owner sees the top bar slide down and hide behind the dialog while scrolling inside "Notification settings" on an iPhone. The harness can't reproduce that here, and it says so honestly:

- Playwright's mobile WebKit has no mouse wheel and Playwright has no touch swipe. The audit instead scrolls every scrollable box in the dialog to its end and calls `scrollIntoView` on the last element, then checks `window.scrollY`, the document's `scrollTop`, `visualViewport.offsetTop/Left/pageTop` and the top bar's `getBoundingClientRect().top`. It also reports `scroll-leak` when the document itself can scroll behind an open overlay. All of these are zero or false at all five sizes.
- What a real iPhone adds is Safari's collapsing address bar and toolbar. They change `100dvh`, so the app shell (`.shell { height: 100dvh }`) grows and shrinks as the user swipes, and the visual viewport can move while the layout viewport stays. With nothing locking the page behind the dialog (no `overflow: hidden` on `html` and `body`, no `overscroll-behavior: contain` on the modal, no `position: fixed` body lock), the swipe at the end of the dialog's own scroll hands over to the page. The top bar sits in the document flow inside that moving shell, so it travels with it.
- The next step is therefore to confirm on a real iPhone (Safari and the installed app), then fix with the M1 list below and re-check on the phone. The harness keeps guarding the parts it can see.

## Proposed M1 fix list (in this order)

1. **Page scroll lock behind overlays.** `html, body { overflow: hidden; overscroll-behavior: none }` (the app scrolls inside `.content`, not the document), `overscroll-behavior: contain` on modal content, the notifications panel and the drawer. Re-test the notification-settings bug on the iPhone. Removes defect 1.
2. **Shell height.** Use `100dvh` with a `min-height: 100svh` fallback and decide whether the top bar should be `position: sticky` or fixed. Add `viewport-fit=cover` to `index.html` and `env(safe-area-inset-*)` padding to the top bar, the drawer, dialogs and the bottom of scroll areas (the installed app on a notched phone).
3. **Phone dialogs.** One rule in `DialogHost`/a shared modal wrapper: below 768 px the dialog is `width: min(100% - 2 * gutter, size)` or a full-screen sheet with `max-height: calc(100dvh - safe areas)` and its own scrolling body. Removes defect 2 for all four dialogs, and covers dialogs the audit doesn't open yet (Share, Members, Create board, Automation builder).
4. **Login card width.** `width: min(var(--card-width), 100% - 2 * gutter)`. Removes defect 3.
5. **Notifications panel at 360 px.** Let the tab strip scroll or wrap, and size the panel to the viewport. Removes defect 4.
6. **16 px inputs on phones.** A single `@media (max-width: 767px)` rule that sets `font-size: 16px` (token) on `input, textarea, select, .ProseMirror`, or Vibe's size props. Removes defect 5 (and the 14 px/15 px list in `mobile-known-defects.json`).
7. Each fix PR deletes its lines from `mobile-known-defects.json`; the audit fails if one is left behind, and fails on any new defect.

Beyond M1 (M2 to M4 in the plan): the board table, Kanban, Calendar and Timeline need real phone layouts (not just "no overflow"), then item view and editors, then automations, dashboards, admin and forms. Add those screens to `mobile-screens.ts` as they are built (Gantt, Workload, dashboards, public form, invite, Settings, update composer, description editor, column popovers are not in the audit yet).

## Caveats

- **WebKit on Linux is not iOS Safari.** Same engine family, but no collapsing toolbars, no safe-area insets, no rubber-band scrolling, no on-screen keyboard and different font metrics. A green audit does not mean the app works on an iPhone; the owner still checks on the real device, in Safari and as the installed app.
- The known-defects list was generated on macOS WebKit. Linux CI may differ by a few pixels (for example a width of 354 against 353), which can add or remove an `offscreen-x` or `overflow-x` entry. The audit job uploads `tests/visual/.audit/findings.ndjson`; if CI disagrees, rebuild the list from that file (`node scripts/mobile-known-defects.mjs <file>`).
- The audit checks one moment per screen. Dropdowns, popovers, the keyboard and rotation are not covered yet.
