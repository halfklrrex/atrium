### Item 1: people value shows a uid in the builder (WP-A)

- **Root cause (confirmed by reading):** `peopleColumn.toText` in `packages/shared/src/columns/people.ts` returns the ids (`personsAndTeams.map((p) => p.id)`), by design, since shared code can't resolve names. Two places in the Automation center use it for display:
  - `apps/web/src/components/automations/ActionLine.tsx` (about line 94): the value token text.
  - `apps/web/src/components/automations/describe-automation.ts` `valueText()` (line 65): the "Reads as" sentence, conditions ("Owner is ...") and the Manage sentence. `DescribeOptions.personName` exists but is only used for notify actions.
  - The CSV export already solved it locally (`apps/web/src/components/boards/board-export.ts` `cellFor`, people branch).
- **Fix:** add one web helper, for example `apps/web/src/lib/cell-display-text.ts` with `cellDisplayText(type, value, settings, { personName, teamName? })`: people resolve to names (unknown: `UNKNOWN_PERSON_NAME`; a team: its name or "a team"), everything else falls back to `columnRegistry.toText`. Use it in `ActionLine`, `valueText` (thread `options` through `valueParts`, `describeConditionParts`, `describeActionParts`), and `board-export.ts` (replace the local branch). `ActionLine` gets `personName` from the builder's existing `describeOptions` (RecipeBuilder line 663) by prop or context. Leave `packages/shared` alone (hot spot, and the id text stays right for search).
- **Also check in the same WP:** person-assigned trigger and "people is" conditions read with names; the notify action's own picker.
- **Tests:** unit tests for the helper; `describe-automation.test.ts` (condition and set-value with a people value read as names); an `ActionLine` test that a picked person shows the name; `board-export.test.ts` keeps passing.
- **Owner check:** Automate, from scratch, "set Owner to" yourself: the token and "Reads as" say your name.

### Item 2a: bulk Undo is refused (WP-B)

- **What Undo does:** `tableActions.setCellBulk` (`apps/web/src/components/board-table/table-actions.ts`, about line 325) captures `previous` per row and Undo calls `itemWrites.setValueMany` (`apps/web/src/data/item-writes.ts`) with one batch of field-path writes; a row whose previous value was empty gets `deleteField()`. One refused row fails the whole batch (batches are atomic). Undo doesn't pass `explain`, so the toast is the generic "You don't have permission to do that."
- **Hypotheses, most likely first:**
  1. **Required column.** The showcase Status column is `required: true` (`scripts/showcase/data.mjs` line 154, in `requiredColumnIds`). The item rule `requiredCellsOk` (`firestore.rules`, about line 755) refuses an update that empties a required cell. If any selected row had an empty Status (or another required column) before the bulk edit, Undo tries to delete it and the whole batch is refused. The forward write is fine because it fills the cell. The test "Undo puts back the previous value of rows that had one and empties the rest" (`bulk-edit.test.tsx` line 293) mocks the write, so the rules never saw this case.
  2. **Locked column for a non-owner.** Not the owner's case (he owns the showcase), listed for completeness.
  3. **Something else in the update rule** (`validItemUpdate`): unlikely, the forward write passed the same rule.
- **First step: reproduce.** A rules test in `tests/rules/` (hot spot): seed a board with a required status, an item with the status empty, write it, then try the Undo batch shape (delete `values.status`). If the test is refused, hypothesis 1 is confirmed. If not, Ophelia reproduces live on the showcase in Chrome and reads the console (`Could not undo the change.` logs the FirebaseError), with the owner's okay (question Q2).
- **Fix (if 1):** never loosen the rule. Build the Undo through a plan like the forward one: for each row, check `checkRequiredWrite(columns, columnId, previous, currentItem)` against the current item; restore the rows that can be restored in one batch and keep the others, then toast "Undid N items; M kept the new value because Status is required" (never silent). Pass `explain` to the Undo `attempt`. Same for the partial-failure Undo.
- **Files:** `table-actions.ts`, `bulk-edit.ts` (a `planBulkUndo`), `bulk-edit.test.tsx`, a rules test in `tests/rules/` (hot spot, test only, no rule change).
- **Owner check:** on the showcase, select 3 rows including one with an empty Status, set Status to Done, click Undo: the filled rows go back, the empty one says why it kept Done.

### Item 2b: highlight the column in all selected rows (WP-B)

- **Target (monday video):** when the pointer is over a bulk-editable cell in a selected row, and other rows of the same level are selected, the cell of that column in every selected row gets an inset outline in the primary blue (same look as the active-cell outline), while the editor is open too. It goes away on mouse leave or when the editor closes. No animation.
- **Fix:** `table-store.ts` gets `bulkColumnId: string | null` (set on pointer enter / editor open in `TableCell.tsx` only when `isBulkEditableType` and the row is selected and `bulkPeers` is non-empty; cleared on leave / close). Each cell subscribes with a selector `s => s.bulkColumnId === columnId && s.selected.has(itemId)`, so only the cells of that column re-render. CSS in `table.module.css`: `box-shadow: inset 0 0 0 var(--border-width) var(--primary-color)` (tokens only). Optional and cheap: the cell `title` / `aria-description` "Changes all N selected items".
- **Files:** `TableCell.tsx`, `table-store.ts`, `table.module.css`, tests in `bulk-edit.test.tsx` or `TableCell` tests. Visual baselines: only if a new screenshot is added (optional; hover states are not in the current set).
