# P8 PR 7a: incoming webhooks and the delivery-log callable (backend only)

Branch `claude/p8-incoming`. Implements the backend of PR 7 of `docs/specs/P8-public-api-and-webhooks.md` (sections 2 D8, 5.2, 6, 8, 9, 10). No UI (PR 7b). Owner decisions: hooks owned by board owners, incoming hooks create items only.

## What changed

- `packages/shared/src/incoming-hooks.ts`: limits (5 hooks per board, 60 calls a minute and 1,000 a day per hook, 64 KB body), callable names, the hook and index documents, the create / update / rotate / delete request and result schemas, the POST body `{ name 1..255, values?, group? }` (strict), the `201 { id, boardId }` answer, and the delivery-log schemas (`listWebhookDeliveries`, rows without payload, default 20, max 50). `activityDataSchema.source` is now `'form' | 'webhook'` plus `webhookName`.
- Data: `boards/{boardId}/incomingHooks/{id}` (name, enabled, createdBy, createdAt, lastUsedAt, defaultGroupId; no secret, no hash) and `incomingHookIndex/{sha256hex}` -> `{ boardId, hookId, createdAt }` (Functions-only). The URL is `https://atrium-workboards.web.app/api/hooks/{hookId}.{secret}`; the secret is 32 random bytes in base64url (43 characters); the index id is the SHA-256 of the whole `{hookId}.{secret}` string. The URL is returned once, at creation and at rotation.
- `firestore.rules`: `incomingHooks` read by `canManageBoard`, no client write; the index has no rule. `tests/rules/src/incoming-hooks.test.ts` (owner reads, editor / viewer / non-member / blocked / pending / signed-out denied, no client writes, collection group denied, index denied); `api-functions-only.test.ts` also covers `apiUsage/hook_<id>`.
- `functions/src/webhooks/`: `incoming.ts` (the four callables as plain functions; `hashIncomingHookToken`), `incoming-store.ts` (seam), `incoming-admin-store.ts`, `incoming-fake-store.ts`, `incoming-testkit.ts`. `manage.ts` gains `listWebhookDeliveries` and exports `requireBoardOwner` and `assertEnabled`; `store.ts`, `fake-store.ts` and `admin-store.ts` gain `listDeliveries(webhookId, limit)`.
- Callables (all `actorFromRequest`, so approved accounts only; all behind `WEBHOOKS_ENABLED`): `createIncomingHook`, `updateIncomingHook` (name, enabled, defaultGroupId or null), `rotateIncomingHookSecret`, `deleteIncomingHook`, `listWebhookDeliveries`. Web wrappers `incomingHookCalls` and `webhookCalls.listDeliveries` in `apps/web/src/lib/callables.ts` (no UI).
- `functions/src/api/hooks.ts` (the route, `createHooksRouter`) and a two-line mount in `functions/src/api/app.ts` (`hooks?: Router` in the deps, `app.use('/api/hooks', deps.hooks)` right after the `API_ENABLED` kill switch and before the 256 KB body check and the bearer auth). `api/index.ts` builds the router; `api/limits.ts` has `adminHookUsageStore`; `api/audit.ts` gains an optional `hookId`.
- `firestore.indexes.json`: composite index `webhookDeliveries (webhookId ASC, createdAt DESC)`.
- Activity: `packages/mcp-core` createService takes `actor.via` (`webhook:<hookId>` only) and stamps it as `updatedVia` on created items; with `via` a locked column is refused even for an owner. `functions/src/lib/activity.ts` tags `item_created` with `data.source: 'webhook'` and `data.webhookName`, and the actor name reads `Webhook: <name>` (actor id stays the creator, photo none). `ActivityStore.getIncomingHookName?` is optional; `admin-activity.ts` implements it.
- Privacy notice: one added bullet (incoming URLs stored only as hashes; webhook deliveries kept 14 days by id). `PRIVACY_LAST_UPDATED` was already 18 November 2026.
- Docs: `docs/DEPLOY.md` section "Incoming webhooks and the delivery log".

## How the route behaves

`POST /api/hooks/{hookId}.{secret}`; no bearer token. Order: API kill switch (503), `WEBHOOKS_ENABLED` (503), body cap 64 KB (413), JSON parse (400), token shape, SHA-256 index lookup (constant-time compare of the id), hook exists and is enabled, creator is still an `approved` account and an owner (`canManageBoard`) of an `active` board, then the per-hook limiter (60 a minute per instance) and the daily counter (`apiUsage/hook_<hookId>`, 1,000), then body validation, `Idempotency-Key` (namespaced `hook_<hookId>`), and `service.createItems` as the creator with `via`. Every failure up to and including the creator check is the same `404 {"error":{"code":"not_found","message":"Not found."}}`. Service errors (bad column or value, derived, server-managed, locked, unknown group) are 400 and nothing is created (one `createItems` batch). `lastUsedAt` is written at most once a minute. Logs carry only the hook id and the error name; audit entries carry hook id, board id, status, ok and ms, and are skipped for 404s so nobody can fill the log by guessing.

## Gotchas and judgment calls

- `updatedVia` is `webhook:<hookId>` (spec says `webhook`): the id lets the log look up the hook's name. The item rules are untouched because only Functions write `updatedVia`.
- Required columns: `createItems` does not enforce them on create (the service's rule: creation is exempt), so a hook can create an item with required cells empty, like the API and MCP.
- A stale `defaultGroupId` (group deleted later) makes calls without `group` answer 400 until the owner changes it.
- Rotating or deleting finds the old index documents with a query on `hookId` (single-field, no composite index). A deleted board leaves its index documents behind; the route 404s on them.
- The route's daily counter reuses the `apiUsage` collection (TTL policy already in the API section).
- `WEBHOOKS_ENABLED` and `API_ENABLED` must both be `true` for the route; the callables need only `WEBHOOKS_ENABLED`.
