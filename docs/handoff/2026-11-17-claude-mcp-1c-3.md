# MCP batch 1c PR 3: move an item to another board

Branch `claude/mcp-1c-3`. Adds `atrium_move_item_to_board` (45 tools) to `@atrium/mcp-core`, so the stdio and hosted modes both have it. No rules, shared-package or Function changes.

## What it does

- Same workspace only; refuses a subitem, the same board, another workspace. A viewer or non-member on the target reads as "not found".
- Copy and retire in one `client.commit`: target item and active subitems (`exists: false`), source item and subitems to `state: 'deleted'` (`updateTime` preconditions). Placed last in the target group (default: the target's first group by position).
- Mapping per column: same id and type, else exactly one same-type column with the same title (case-insensitive). Status, dropdown and tags map by label text; labels missing on the target are dropped and reported, never created. Votes keep their voters. Dropped and reported: server-managed, `dependency`, unmatched, locked (non-owner on the target), changing type, a second source column hitting an already filled target, and the item description. Derived columns are skipped silently (nothing stored).
- Guard: refuses unless `allowDataLoss: true` when anything is dropped or the item has updates. `dryRun` writes nothing.

## Deviations and notes

- The dry run result adds `needsAllowDataLoss` (so a preview says whether the real call would refuse). `newItemId` is `null` on a dry run.
- The description is reported as dropped (`not copied`), which means an item with a description always needs `allowDataLoss`. Copying it is part of the deferred "faithful move" (images are Functions-only).
- Update counts use the item's `updatesCount` when present, else the updates subcollection.
- Tests: unit tests in `mcp-core.test.mjs` (fake client), one emulator case in `tests/rules/src/mcp-admin-client.e2e.test.ts`, tool counts in `stdio.test.mjs`, `app.test.ts` and `index.d.mts`.
