# P8 PR 4: API write routes, idempotency, error codes

Branch `claude/p8-api-writes` (from `origin/main` with the read routes). Spec: `docs/specs/P8-public-api-and-webhooks.md` sections 4, 6, 8 (PR 4), 9. No hard delete and no structure changes over the API in v1 (owner decision: all section 12 defaults approved).

## What changed

- **Error codes.** `McpUserError(message, code?)` takes an optional machine code (`not_found`, `forbidden`, `invalid`, `conflict`, `read_only`), set at the throw sites the API used to recognize by wording (board, item, update, doc, dashboard, team and view "was not found" and "not active", "You can only view", "needs the ... role", "is locked to", and "is changing type; try again" as `conflict`). Messages and MCP behavior are unchanged (all `mcp-core` tests, the tools snapshot and parity pass). `toApiError` uses `code` first and keeps the wording map as a fallback for sites with no code. A thrown error with `status 409` (a write precondition that lost its one retry) is now a 409 `conflict`.
- **Routes** (`functions/src/api/routes/writes.ts`, scope `write`): `POST /boards/:id/items` (one item, or `{ items }` up to 50), `PATCH /items/:id`, `POST /items/:id/subitems` (`{ items }` up to 50), `POST /items/:id/duplicate`, `POST /items/:id/archive`, `POST /items/:id/updates` (`{ text }`, up to 50,000 characters, `@[Name]` mentions). Bodies are zod `strictObject`s (unknown fields are 400 with the path). Every route calls the same service method as its MCP tool; the service is still the only permission gate (viewer 403, non-member and out-of-scope workspace 404, locked, derived, server-managed and required columns refused with its messages). `?board=` is a hint on the item routes.
- **Answers.** Creates answer 201 with the item in the `GET /items/{id}` shape (a batch: `{ boardId, items }`; subitems: `{ boardId, parentItemId, items }`; duplicate: the copy). `PATCH` answers 200 with the item. Archive answers `{ id, state: "archived", subitemsAlso, boardId }` (the item is gone from GET afterward). A new update answers 201 in the `GET /items/{id}/updates` post shape.
- **Idempotency** (`functions/src/api/idempotency.ts`): `Idempotency-Key` on `POST` only (`[A-Za-z0-9_-]`, 1 to 64 characters; anything else is 400). Record `apiIdempotency/{uid}_{key}` with the request hash (method, concrete path, query and key-sorted body), a `pending` marker with a 60 s lease, then `done` with status and body (as JSON text) and `expiresAt` = 24 h (Timestamp, TTL). Same key and hash returns the stored response with `Idempotency-Replayed: true`; same key, different request is 422 `invalid`; a twin while the first runs is 409 `conflict`; an expired lease is taken over. Errors are never stored (the marker is deleted). `begin` runs in a Firestore transaction.
- **Rules and deploy:** `apiIdempotency` has no rule (Functions only); `tests/rules/src/api-functions-only.test.ts` proves every client is denied. `docs/DEPLOY.md` has the TTL command.
- **Privacy:** `privacy-content.ts` states that API calls are logged for 90 days (route, board id, result, time, token id, user id; never the body or the token); date `18 November 2026`; `PrivacyPage.test.tsx` pins the sentence.

## Gotchas and next

- A replay still counts as a call and a write against the daily caps (the guard runs first). Fine for v1.
- If `complete()` fails after the write succeeded, the marker stays `pending` until the lease ends (60 s); a retry after that would run the write again. Logged, accepted.
- The Privacy page text changed, so the Linux baseline for the mobile `privacy` screen may need **Actions: Update visual baselines** on the PR.
